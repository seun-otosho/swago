# swago: design notes

A Go CMS inspired by Wagtail. Date: 2026-10-22. Status: planning, no code yet.

## Decision: Go-native rethink, not a port

Full parity with Wagtail and a Go-native rethink pull in opposite directions. We take the rethink and treat parity as a checklist to tick off later. We do **not** promise API or database compatibility with Wagtail. That compatibility is where most of the cost of full parity goes.

| | Full parity (port) | Go-native rethink (chosen) |
|---|---|---|
| Schema definition | Runtime, DB-driven (Django models and migrations). Go has no metaclasses, so it would need reflection or codegen to imitate them. | Page types are Go structs registered in code. Codegen produces migrations and admin forms. Checked at compile time. |
| Extensibility | Relies on Python monkey-patching, hooks and signals. Third-party packages can't be ported as they are. | Go modules, explicit interfaces and middleware. Extensions are compiled in. |
| Page templates | Django templates, `{% include_block %}`. | `html/template` or templ, with typed blocks. |
| StreamField | JSON blob, runtime block definitions. | Same JSON on disk, but blocks are Go types with a tagged union for (de)serialization. |
| Admin UI | Re-create Draftail, page chooser, explorer and so on. The largest part of the work. | Embedded SPA or htmx, with server-rendered forms generated from struct tags. |
| Data compatibility | Can read existing Wagtail databases. | Clean schema, plus an optional one-way importer. |
| Cost | Multi-year, and Wagtail keeps moving. | Months for a usable core. We choose what to leave out. |
| Deployment | Single binary. | Single binary. |

Wagtail features to reach eventually (the parity checklist): page tree, StreamField, admin UI, images and renditions, documents, search, workflows, permissions, i18n, forms, snippets.

## Datastore

- **SQLite is the default**, for dev and zero-ops deployments.
- Also support everything Django/Wagtail supports (Postgres, MySQL/MariaDB), and others later.
- Query layer and ORM: **Ent** (decided 2026-10-22, replacing an earlier GORM decision). Schemas are Go code, queries are generated and typed, and it targets SQLite, Postgres and MySQL/MariaDB. Use a pure-Go SQLite driver (modernc-based) to keep the single binary free of cgo. Check the Ent dialect page for exact version support before committing.
- Migrations: Ent's auto migration (`client.Schema.Create`) is append-only (new tables, indexes, columns, wider types). Dropping needs `WithDropColumn` and `WithDropIndex`. Ent integrates Atlas for versioned migrations, so:
  - **Dev:** auto migration on startup, for fast iteration.
  - **Production:** versioned migration files generated by Atlas from the Ent schema, reviewed and committed, with `atlas migrate apply`. Ent does not detect renames: a rename looks like a drop plus an add. Handle them with the `StorageKey` field option (keep the old column name) or a `schema.WithDiffHook` that turns the drop plus add into a rename, and write data backfills by hand.
  - Core and user page-type schemas both go into the same Atlas migration directory, so ordering stays in one place.
- Page tree: materialized paths (like treebeard), because they work on every database.
- Block JSON is stored as TEXT/JSON, again so it works everywhere. No Postgres-only features (ltree, JSONB operators) in core.

## Build order

1. Page tree, plus typed page models registered in code.
2. Blocks (the StreamField equivalent) and revisions with draft/publish.
3. Headless JSON API and server-rendered templates.
4. Auth, permissions and groups.
5. Admin UI.
6. Images and renditions, documents, search, i18n, workflows.

## Open questions

- Module path and Go version. Not yet chosen.
- Production migration tool: Atlas versioned migrations (the Ent default) vs hand-written goose files. Leaning Atlas.
- Ent has no model inheritance, so a page type is a separate entity linked to a base page entity (composition). Settle this together with page field storage.
- How downstream projects add page types: they run `go generate` with Ent in their own module. Decide whether the framework ships a small CLI or a documented template to make this painless.
- Page field storage: multi-table inheritance vs one table with a JSON column (review point 2).

Closed on 2026-10-22: templ for all templates and htmx for the whole framework, including the admin (small JS islands only where unavoidable, e.g. rich text); Ent as the ORM.

## Sites and routing

Based on the Wagtail docs ([Site model](https://docs.wagtail.org/en/stable/reference/pages/model_reference.html), [multi-site, multi-instance and multi-tenancy](https://docs.wagtail.org/en/stable/advanced_topics/multi_site_multi_instance_multi_tenancy.html)).

**Site model** (what Wagtail does, and what we keep):
- `hostname` (no scheme, port or path), `port`, `root_page` (served at `/`), optional `site_name`, and `is_default_site` (only one allowed).
- Matching a request: unique hostname first, then hostname plus port, then the default site, else an error. Cache the result on the request context.
- Page `url_path` is built from slug plus parent path; changing a slug rewrites it for the page and all descendants. Slugs must be unique among siblings, and Wagtail adds a suffix on collision.
- URL helpers: local path when one site is served, full URL otherwise; `relative_url(current_site)` picks local or full by site; `get_url_parts()` is the override point for custom routing.
- Locale: `language_code` per locale, and a `translation_key` shared by translations (unique per `translation_key` + `locale`).

**What Wagtail actually offers for the three levels:**

| | Multi-site | Multi-instance | Multi-tenancy |
|---|---|---|---|
| Isolates | Permissions and page trees only | Everything (content, DB, media, users) | Content and users per tenant, one instance. Wagtail does not fully support this |
| Shape | One codebase, DB and media root | Separate settings, DB, media and process per site | One instance, many tenants |
| Caveat | Content can leak between sites if set up carelessly | Resource use grows with every site | Snippets, workflows, site history and redirects are not tenant-aware; sites, users and groups must be superuser-only |

**swago position:** Wagtail's multi-tenancy is a workaround (a site foreign key plus filtered querysets). We make tenancy a first-class concept instead, because retrofitting it later touches every table.
- Multi-site (hostname to root page) is in core from step 1, as in Wagtail.
- Add a `tenant_id` column to every content-bearing table (pages, snippets, redirects, revisions, workflows, collections, users, groups) from the first migration, through a shared Ent mixin, and apply it through Ent privacy rules and interceptors so every query and mutation is filtered by default. Single-tenant installs use one implicit tenant.
- Tenant resolution happens in middleware (hostname to site to tenant) and puts the tenant into the request context; background jobs take it explicitly.
- Multi-instance stays a deployment choice (run the binary several times), not a feature.
- Decided 2026-10-22: one shared database with `tenant_id`, with the tenant scope kept behind one function (`tenant.Scope`) so database-per-tenant (the client is created per tenant database) can be added later.

### Preventing tenant data leaks

No single mechanism is enough, so there are layers. Each one catches what the previous one misses.

1. **Fail closed.** An Ent interceptor adds `WHERE tenant_id = ?` to every query from the request context, and a privacy policy denies the operation if the context has no tenant. Escaping takes an explicit, greppable "allow without tenant" context helper, used only by system jobs and superusers.
2. **Writes are stamped.** An Ent mutation hook (from the shared mixin) sets `tenant_id` from the context and rejects a mutation that carries a different one. Updates and deletes go through the same filter, so a guessed ID from another tenant matches zero rows.
3. **The schema enforces it.** Unique indexes are `(tenant_id, ...)`, for example `(tenant_id, parent_path, slug)`. Foreign keys are composite, `(tenant_id, id)`, so a row can't reference another tenant's row. This backs up edge traversals and joins, where the interceptor is the only other guard.
4. **Raw SQL is the hole.** Ent's generated builders are the normal path, which removes most raw SQL, but the underlying SQL driver and custom `sql` predicates still bypass the filter. A lint rule (golangci-lint `forbidigo`) bans direct driver access outside the `tenant` and migration packages. Where it's needed, it goes through a helper that requires the tenant.
5. **Caches, search indexes and file storage** all include the tenant in their keys and paths (`tenant/<id>/media/...`).
6. **Optional hardening on Postgres:** row-level security with `SET LOCAL app.tenant_id` per transaction, so the database itself refuses cross-tenant rows. It's Postgres-only, so it's an opt-in extra, not part of core.
7. **A leak test that can't be forgotten.** A test iterates over every registered model, creates rows for two tenants, and asserts that list, get, update and delete from tenant A never touch tenant B's rows. A new model is picked up automatically because models register themselves.

### Renames, drops and data backfills

Django's `makemigrations` diffs models against the recorded migration history, writes the migration file, derives reverse operations for most steps, and asks "did you rename X to Y?". It still needs a hand-written reverse for `RunPython` backfills, and reversing a column drop does not restore its data. Ent with Atlas covers most of that, with two differences. Ent's own docs say it does not detect renames (a rename looks like a drop plus an add, which loses data). And Atlas works as a roll-forward history: `atlas migrate down` computes a downgrade plan from the database's current state instead of replaying pre-written reverse files, only reverts what the migration directory applied, and does not restore dropped data. Manual down logic can be written in the migration file when the computed plan isn't enough. So a person finishes each migration, and the process stops mistakes:

- Production migrations are Atlas versioned SQL files generated from the Ent schema. A person edits the draft (turning a drop plus add into a rename, adding the backfill), and `atlas migrate lint` and pre-migration checks flag destructive steps. Backfills that need application logic run as a Go step through the Ent client.
- **Expand and contract**, so nothing is lost and rollbacks work: (1) add the new column, (2) backfill and dual-write, (3) switch reads, (4) drop the old column in a later release.
- Backfills run per tenant in batches, with the tenant set explicitly, so they can't cross tenants either.
- **CI guard:** after applying all migrations to an empty database, `atlas schema diff` against the Ent schema must be empty. If a developer changes a schema without generating a migration, CI fails. Destructive steps (drop, type narrowing) are flagged by Atlas lint and need an explicit approval comment in the migration.
- Test each migration on a copy of realistic data, on all three databases, in the CI matrix.

## Review: gaps and open questions

Review dated 2026-10-22, written against the planning-stage doc above. The core call (rethink over port) is sound, and the comparison table is the strongest part.

1. **Two open questions are already answered by the project's own goal.** The project is "Go, templ, htmx", yet the open questions list htmx vs SPA and `html/template` vs templ. Recommend closing both: templ for templates, htmx for the admin, with small JS islands where needed (see point 6).
2. **How page fields are stored is not decided, and it is the biggest schema decision.** Wagtail uses multi-table inheritance (a base page table plus one table per page type). The alternative is one pages table with typed fields in a JSON column. This choice drives codegen, migrations, revisions, querying by field, and the importer. It belongs in track 2 before any code.
3. **"Codegen produces migrations" hides real work.** When a struct changes, something has to diff the old and new schema, handle renames, and generate migrations for three dialects. No tool is named (Atlas, goose plus a custom differ, bun migrations). Also unclear: how core migrations and user page-type migrations are ordered and versioned.
4. **Materialized path details are missing.** Path alphabet and step width (which caps children per node), how `depth` and `numchild` are kept in sync, the cost of moving a subtree, and concurrent sibling inserts (a known race in treebeard, and SQLite has a single writer).
5. **Sites and routing are absent.** Wagtail's Site model (hostname to root page), slug uniqueness among siblings, cached URL paths, and serving a request by walking the tree all need a home, probably in step 1.
6. **Rich text and the StreamField editor are not addressed.** Draftail has no htmx equivalent. A rich text editor needs JS (Tiptap, ProseMirror or Lexical), and a nested, reorderable StreamField editor is the hardest UI in Wagtail. This is the main risk to the htmx choice and should be what the prototype tests first.
7. **Single binary vs SQLite driver.** `mattn/go-sqlite3` needs cgo, which complicates cross-compiling a single binary. `modernc.org/sqlite` is pure Go. Same question later for image renditions (libvips via cgo vs pure-Go imaging). Worth stating as a principle: pure Go in core unless there is a strong reason.
8. **Multi-dialect from day one multiplies cost.** Every query, migration and test runs against three databases. `bun` supports all three and fits the "works everywhere" rule; `sqlc` would need one query set per dialect. Recommend `bun` and a CI matrix from the start, or ship SQLite plus Postgres first and add MySQL later.
9. **Search conflicts with "no Postgres-only features".** Full text search differs on each database (SQLite FTS5, Postgres tsvector, MySQL FULLTEXT). Needs a backend interface like Wagtail's, with a basic fallback.
10. **Features placed late shape early schema.** i18n (Wagtail adds `locale` and `translation_key` to every page), permissions (page permissions are granted on tree paths), and workflows and scheduled publishing (which hang off revisions) all affect the tables built in steps 1 and 2. Reserve the columns and hooks early even if the features come later.
11. **Build order leaves no way to edit content until step 5.** A headless API at step 3 also needs auth for previews and writes, but auth comes at step 4. Suggest a thin vertical slice instead: tree, one page type, draft/publish, a minimal login and a bare admin edit form, then widen each layer.
12. **Not mentioned at all:** preview, page locking, redirects, audit log, sitemaps, caching, the extension/hook registry design (the doc says "explicit interfaces" but not which ones), file storage backends (local vs S3), and a testing strategy.

## Relation to the three tracks

All three tracks stand; this doc supports each one and gives each a concrete starting point.

**Track 1: Map Wagtail features to Go.** The comparison table and parity checklist are this track's seed. The track should turn the checklist into a per-feature table (Wagtail concept, Go design, build step, in or out of the first release) and close the open questions above: query layer, migration tool, SQLite driver, and the hook/extension model. Review points 3, 7, 8, 9 and 12 land here.

**Track 2: Build the page tree model.** This is step 1 of the build order and the critical path. The doc gives the direction (structs registered in code, materialized paths) but leaves the decisions that block code: page field storage (point 2), path encoding and concurrency (point 4), sites and routing (point 5), and reserved columns for locale, revisions and permissions (point 10). It depends on track 1 picking the query layer, so settle that first.

**Track 3: Prototype the admin with htmx.** The doc puts the admin at step 5 and still lists htmx as open, so an early prototype is how that question gets closed. Run it as a spike against a stubbed page tree, not a finished one, and aim it at the hardest parts: the page explorer, a nested StreamField editor, and rich text (point 6). If those work with htmx plus small JS islands, the choice is settled.

## Suggested next steps

1. Update this doc to close templ and htmx as decided, and record the pure-Go principle.
2. Start track 1 and track 2 together; track 1's first job is the query layer and migration tool, since track 2 needs them.
3. Start track 3 once track 2 has a sketch of the page-type registration API, so the prototype's forms match the real struct shape.
